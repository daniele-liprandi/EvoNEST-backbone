# Mastra AI Home Page — Design Spec

**Date**: 2026-05-27
**Scope**: EvoNEST home page (`src/app/(nest)/home/`) + new Mastra service
**Status**: Approved, ready for implementation planning

---

## 1. Goal

Replace the static dashboard home page with a conversational AI interface backed by a Mastra agent. Researchers can query, filter, visualise, and submit samples and traits using natural language. Structured forms on individual data pages remain unchanged. The existing per-page `NlFilterBar` also remains unchanged.

---

## 2. Layout

### Desktop

Three vertical regions, top to bottom:

1. **Command bar** — full-width text input + send button
2. **Two-column row** (flex, 3:1 ratio):
   - Left: conversational canvas (fills remaining height, scrollable)
   - Right: `CardSamples` sidebar — always visible, shows recent samples
3. **Accordion** — collapsed by default, contains stats row (Users / Samples / Experiments / Traits) and "Samples collected last week" card

### Mobile

1. **Command bar** — full width
2. **Conversational canvas** — full width, scrollable
3. **Accordion** — collapsed, contains stats cards + `CardSamples`

`CardSamples` moves into the accordion on mobile. No sidebar on narrow screens.

### Empty state

When no conversation has started, the canvas area shows the existing `MapboxScatterPlot` (world map of collection locations) with a centred overlay reading "Your collection — ask a question above to explore". The first user message replaces the map with the conversation history.

---

## 3. Conversational canvas

- Message history accumulates (conversational, not single-shot)
- Each turn: user message bubble + one or more AI response blocks rendered below it
- Scrollable; new messages anchor to bottom
- Thread ID stored in `sessionStorage`, sent with every request so Mastra maintains history server-side

### Response block types

The Mastra agent returns a typed packet:

```typescript
type MessageBlock =
  | { type: "text";     content: string }
  | { type: "table";    entity: "samples" | "traits"; data: Record<string, any>[]; totalCount: number }
  | { type: "chart";    chartType: "bar" | "scatter" | "line" | "treemap"; title: string; data: any[]; config: Record<string, any> }
  | { type: "readback"; entity: "samples" | "traits"; records: Record<string, any>[]; pendingCreate: true }
```

A single agent response can contain multiple blocks (e.g. a `text` block followed by a `table` block).

`ChartBlock` uses **recharts** for `bar`, `scatter`, and `line` types, and **Plotly** (already a dependency) for `treemap`. The `config` field carries library-specific props — the block component switches on `chartType` to pick the right renderer.

### Result truncation

`TableBlock` renders a maximum of **5 rows on desktop / 2 rows on mobile**. If `totalCount` exceeds the limit, a link appears below the table:

```text
View all 14 results in samples table →
```

The link navigates to `/samples/general` (or `/traits`) with filter params encoded in the `useUrlFilters` URL format (e.g. `?genus=Argiope&type=silk`). These params are generated by the agent as part of the tool response and included in the `table` block.

---

## 4. Write actions — readback pattern

When the agent wants to create records it does not write immediately. It returns a `readback` block.

**Desktop**: rendered as an editable-looking table with column headers, one row per record, and three buttons: **Confirm and save** / **Fix** / **Cancel**.

**Mobile**: rendered as compact cards, one per record (species name bold, other fields as small descriptive text), with **Confirm** and **Fix** buttons.

Corrections are made in natural language in the next message. The agent updates the records and returns a new `readback` block. This repeats until the user confirms. On confirm, the frontend calls the appropriate creation endpoint (`/api/samples` or `/api/traits`) with the finalised records from the block.

The agent never writes to MongoDB directly. All writes go through the existing Next.js API routes, after explicit user confirmation in the UI.

## 5. Architecture

### Services

| Service | Container | Notes |
| --- | --- | --- |
| Next.js app | existing | unchanged |
| Mastra agent | new Docker container | added to `docker-compose.yml` |
| MongoDB | existing | shared Docker network |
| Anthropic API | external | Claude Sonnet via Vercel AI SDK |

### Request flow

```text
Browser
  → POST /api/ai/chat  (Next.js proxy)
      ├─ Auth0 session check — 401 if not authenticated
      ├─ Attach thread ID from request body
      └─ Forward to Mastra service → stream response back
          ├─ Mastra agent calls tools as needed (MongoDB reads)
          ├─ Returns typed MessageBlock[] packet
          └─ Write confirmations hit /api/samples or /api/traits directly from browser
```

Mastra is never exposed publicly. The Next.js proxy is the only entry point.

### Mastra agent tools

| Tool | Description |
| --- | --- |
| `querySamples(filters)` | Query MongoDB samples collection; `filters` is a Zod-typed object matching `useUrlFilters` param syntax. Returns records + total count + suggested URL filter string. |
| `queryTraits(filters)` | Same pattern for traits collection. |
| `createSamples(records[])` | Validates and returns a `readback` block. Does not write. |
| `createTraits(records[])` | Same for traits. |
| `checkTaxonomicName(name)` | Calls the existing name-checker API (same endpoint as the old `NameCheckerCard`). Returns validity + canonical form. |
| `generateTreemap(entity, hierarchy)` | Builds Plotly-compatible hierarchical data for samples or traits, grouped by specified fields. Returns a `chart` block with `chartType: "treemap"`. |
| `getSchema()` | Calls `/api/schema` to retrieve live filterable columns per entity type. Used to enrich system prompt context at conversation start. |

### Conversation history

Stored in Mastra's built-in in-memory thread store, keyed by `threadId` (a UUID generated client-side and persisted in `sessionStorage`). Can be migrated to MongoDB-backed storage later without touching the frontend.

## 6. Existing infrastructure reused

| What | How it's used |
| --- | --- |
| `useUrlFilters` hook | Already on all data pages. "View all →" links from `TableBlock` produce compatible URL params. |
| `/api/schema` | Mastra calls this at conversation start to get live column lists for the system prompt. |
| `/api/nlfilter` | Kept for per-page `NlFilterBar` on samples/traits/experiments pages. Not used by Mastra. |
| `NlFilterBar` | Unchanged, stays on individual data pages. |
| `NlGlobalSearchCard` | Removed from home page — superseded by the Mastra canvas. |
| Table bug fixes (`getRowId`, `useEffect` sync) | Already applied; `TableBlock` inherits these. |
| `/api/samples`, `/api/traits` | Write confirmations call these directly from the browser, same as the structured forms. |

## 9. Error handling

- **Agent timeout / 5xx from Mastra**: show a `TextBlock` with an inline error message ("Something went wrong, try again"); do not crash the canvas
- **Auth failure at proxy**: redirect to login (existing Auth0 flow)
- **Write confirmation failure** (e.g. duplicate name): show error inline below the readback block, keep records visible so user can correct
- **Schema fetch failure** (`getSchema` tool): agent proceeds without live column list, falls back to hardcoded field descriptions in the system prompt

---

## 10. Out of scope for v1

- Experiments (read or write)
- Streaming text token-by-token (full block delivered at once is fine for v1)
- Persisting conversation history across browser sessions
- Multi-user shared conversation threads
- Chart editing or customisation after render
